# 8. REQUIRED GAME ENTRY POINTS

Every game must provide:

```cpp
void enter();
void update(const GameInput &input);
```

## `enter()`

`enter()` is called every time the user launches the game.

It must completely reset the game's runtime state.

It should:

1. reset gameplay state
2. reset timers
3. reset score/lives/etc.
4. reset cached rendering state
5. set rotation if necessary
6. clear the screen ONCE
7. draw the game's initial/static screen
8. make the game immediately ready to run

Example:

```cpp
void enter() {
    state = PLAYING;
    score = 0;
    lastFrameMs = millis();

    display.setRotation(0);
    display.fillScreen(ST77XX_BLACK);

    drawStaticScene();
    drawPlayer();
    drawHUD();
}
```

Do not assume old variables contain their initial values just because they were initialized globally. The game may be launched multiple times during the same ESP32 session.

# 10. THREE-POSITION SWITCH INPUT

The two toggle switch states are NOT currently contained in `GameInput`.

Therefore the game may directly read their pins from `Hardware.h`.

Use a local namespaced helper such as:

```cpp
SwitchState readGameSwitch(int upPin, int downPin) {
    const bool up = digitalRead(upPin) == LOW;
    const bool down = digitalRead(downPin) == LOW;

    if (up && !down) return SWITCH_UP;
    if (!up && down) return SWITCH_DOWN;
    if (!up && !down) return SWITCH_CENTER;

    return SWITCH_ERROR;
}
```

Then:

```cpp
SwitchState left =
    readGameSwitch(LEFT_UP_PIN, LEFT_DOWN_PIN);

SwitchState right =
    readGameSwitch(RIGHT_UP_PIN, RIGHT_DOWN_PIN);
```

DO NOT reverse the physical switch directions unless the game specification explicitly asks for reversed controls.

Physical mapping:

```text
LEFT:
    UP     GPIO 33 LOW
    CENTER GPIO 33/32 HIGH
    DOWN   GPIO 32 LOW

RIGHT:
    UP     GPIO 26 LOW
    CENTER GPIO 26/25 HIGH
    DOWN   GPIO 25 LOW
```

If actions should happen only once when a switch changes position, maintain previous switch states inside the game and perform edge detection.

# 12. MAIN LOOP / TIMING

`update()` is called very frequently by the launcher.

It MUST be nonblocking.

Never use gameplay loops such as:

```cpp
while (playing) {
    ...
}
```

inside `update()`.

Never wait for user input using a blocking loop.

Avoid `delay()` during gameplay.

Instead use `millis()` or `micros()`.

Example:

```cpp
uint32_t lastFrameMs = 0;

void update(const GameInput &input) {
    const uint32_t now = millis();

    handleInput(input, now);

    if (now - lastFrameMs >= FRAME_INTERVAL_MS) {
        lastFrameMs = now;

        updateSimulation(now);
        renderFrame();
    }
}
```

The function must return to the launcher after every update.

---

# 13. FRAME RATE

Aim for smooth gameplay on the ESP32/ST7789.

For motion-heavy games, target approximately:

```text
30 FPS minimum
40-60 FPS where practical
```

Do not arbitrarily lock a game to a slow frame rate when the operations are inexpensive.

Keep simulation and rendering timing separate where useful.

For example:

```cpp
constexpr uint32_t FRAME_US = 20000; // 50 FPS
```

using `micros()`.

Do not assume the TFT can efficiently redraw all 76,800 pixels every frame through ordinary Adafruit GFX calls.

Optimize around SPI bandwidth.

# 14. MOST IMPORTANT RENDERING RULE

DO NOT repeatedly call:

```cpp
display.fillScreen(...)
```

inside the gameplay update loop.

That causes visible flashing, tearing, and poor frame rate.

`fillScreen()` should normally happen only:

- when entering the game
- when intentionally changing to a completely different game screen/state

During gameplay, redraw only what changed.

---

# 15. DIRTY-REGION RENDERING

For moving objects, retain their previous screen position.

Before drawing the new frame:

1. erase/redraw the object's old region
2. update the object
3. draw it at its new position

Example:

```cpp
erasePlayer(oldX, oldY);
drawBackgroundRegion(oldX, oldY, PLAYER_W, PLAYER_H);

drawPlayer(newX, newY);
```

If the background is simple, clearing a small rectangular region is acceptable:

```cpp
display.fillRect(
    oldX,
    oldY,
    PLAYER_W,
    PLAYER_H,
    BACKGROUND_COLOR
);
```

If the region contains scenery, recreate that scenery rather than simply filling it black.

# 16. HUD RENDERING

Static HUD graphics should be drawn once.

Values such as:

- score
- health
- ammo
- lives
- timer
- objective status

should only redraw when the underlying value changes.

Maintain cached values:

```cpp
int shownHealth = -1;

void drawHealthIfChanged() {
    if (health == shownHealth)
        return;

    display.fillRect(...);
    display.print(health);

    shownHealth = health;
}
```

Do not redraw the entire HUD every frame.

Design the HUD as part of the game presentation rather than dumping diagnostic text around the screen.

Unless the game design says otherwise, keep gameplay information compact and avoid covering a large portion of the 240×320 playfield.

---

# 17. DRAWING PERFORMANCE

The ESP32/ST7789 is not a desktop GPU.

Prefer inexpensive primitives:

```cpp
drawFastHLine()
drawFastVLine()
fillRect()
drawRect()
fillCircle()
drawCircle()
drawLine()
```

Use large numbers of individual `drawPixel()` calls cautiously.

Avoid clearing and reconstructing the entire scene every frame when a smaller update is possible.

Where possible:

- combine adjacent pixels into lines or rectangles
- render static scenery once
- use small dirty regions
- avoid unnecessarily drawing objects hidden offscreen
- avoid expensive floating-point operations in inner rendering loops
- precompute constants
- use integer/fixed-point math for hot paths when useful

Correct visual behavior matters more than unnecessarily elaborate rendering techniques.

# 28. ROBUSTNESS

- switch reports `SWITCH_ERROR`
- button held across a state transition
- player reaches screen/world boundary
- arrays are full

- `millis()` rollover-safe subtraction

Use patterns such as:

